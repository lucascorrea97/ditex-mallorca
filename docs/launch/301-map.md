# 301 redirect map — WordPress `.es` → new site

**Issue:** #23 (preparation half only) · **Status:** DRAFT — research + planning artifact, no
live behaviour changed · **Relates to:** ADR-0004 (`.es` canonical), ADR-0005 (WordPress stays
live until cutover), ADR-0014 (content parity)

> This document and its companion `redirects.draft.json` are **preparation only**. Wiring the
> redirects into the actual build, and flipping DNS/`app/robots.ts`, happens at cutover once
> the full launch scope is signed off (#23's other acceptance criteria) — not in this PR.

## Method

Crawled the live `https://ditexmallorca.es` directly: fetched `robots.txt`, `sitemap_index.xml`
and the sub-sitemap it references, then fetched every URL found there plus every internal link
surfaced on the homepage (nav + footer + body CTAs), to catch pages that exist but aren't in
the sitemap. Cross-checked with a site-restricted search to see what's actually indexed today.
No crawler/tool access beyond fetching individual pages — this is a small site (9 sitemap
entries), so a manual crawl is complete, not a sample.

## What the crawl found

- **`robots.txt`**: `User-agent: *` / `Disallow:` (nothing blocked) / `Sitemap:
  https://ditexmallorca.es/sitemap_index.xml`.
- **Sitemap**: a Yoast-generated index pointing to one sub-sitemap, `page-sitemap.xml`, with
  **9 URLs**. No `post-sitemap.xml`, no category/tag sitemap — **confirmed there is no blog,
  no posts, no taxonomy archives, and no pagination anywhere on the site.** It's a static
  WordPress brochure site, not a CMS with ongoing content.
- **No language switcher, no CA/EN URLs** — the current site is Spanish-only. The new site's
  Catalan and English routes (ADR-0009) are net-new; there is nothing old to map them from.
- **No WooCommerce/shop, no indexed uploads.** Searched specifically for an indexed Price List
  PDF (CONTEXT.md: Price List is normally a gated PDF) — found none publicly indexed, consistent
  with it living only behind the password-gated `/clientes/` page.
- **4 orphan URLs live but not in the sitemap and not indexed** (found only by following
  internal links from the homepage's body CTAs, which point to different slugs than the main
  nav menu): `/servicios/`, `/sobre-nosotros/`, `/contacto/`, and `/clientes/`. The first three
  are near-duplicate content of pages that ARE in the sitemap under different slugs
  (`/materiales-textiles/`, `/mas-de-30-anos-al-sector-textil/`, `/contacto-2/`) — this looks
  like a leftover from a past slug rename where the old slugs were never cleaned up or
  redirected. They still 200 today, so they must still be redirected at cutover — otherwise
  any bookmark, backlink, or stray crawl of them 404s the moment WordPress is decommissioned.

**Total: 13 real URLs** (9 sitemapped + 4 orphans) across the whole crawlable site.

## WWW / non-WWW, HTTP→HTTPS, and trailing slashes

Checked the live site's current behaviour directly (`curl -I`):

| From | To | Already true today? |
|---|---|---|
| `http://ditexmallorca.es/` | `https://ditexmallorca.es/` | Yes (301) |
| `http://www.ditexmallorca.es/` | `https://www.ditexmallorca.es/` | Yes (301) |
| `https://www.ditexmallorca.es/` | `https://ditexmallorca.es/` (bare apex) | Yes (301) |
| `https://ditexmallorca.es/productos` (no slash) | `https://ditexmallorca.es/productos/` (slash) | Yes (301) |

So today's **canonical form is `https://ditexmallorca.es/path/`** — bare apex domain, HTTPS,
trailing slash. That's the form Google actually has indexed, and it's what the "old URL"
column above uses.

**At cutover, this is a DNS/Vercel-project-settings task, not a `next.config.js` concern**:
- Assign both `ditexmallorca.es` and `www.ditexmallorca.es` to the Vercel project, with `www`
  set to redirect to the bare apex (replicates today's behaviour exactly) — Vercel's domain
  settings do this natively; don't hand-roll it in redirects.
- HTTP→HTTPS is handled automatically by Vercel for any assigned domain.
- Trailing slash: the new site's own convention is **no trailing slash** (standard Next.js App
  Router default, confirmed — `next.config.ts` has no `trailingSlash` override). The redirect
  entries in `redirects.draft.json` therefore match the old trailing-slash source paths and
  point at trailing-slash-free destinations, in one hop — no need to redirect trailing-slash
  variants of the *new* site, since Next.js's own router only ever produces the one canonical
  form.

## Why the redirect destinations are hardcoded to `/es/...`, not locale-relative

The old WordPress site had no CA/EN content — everything on it is Spanish. Next.js's
`redirects()` supports locale-aware source patterns (see `redirects.draft.json`'s header
comment), but using that here would mean an old URL hit by a browser with an English
`Accept-Language` header lands on `/en/...` — a page that never had an English predecessor.
That's not preserving equity, it's inventing a translation relationship that doesn't exist.
Redirecting straight to the definite historical-language URL (`/es/...`) in a single hop is
both simpler (no chained proxy-locale-redirect) and more correct.
